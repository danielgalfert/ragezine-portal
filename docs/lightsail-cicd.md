# Lightsail CI/CD

The workflow in `.github/workflows/ci-cd.yml` runs Django tests against PostgreSQL and checks the React build on pull requests to `main`. A push to `main` repeats both checks and deploys the verified commit. Require pull requests for changes to `main` in GitHub branch protection so that merging a PR is the deployment trigger.

The deployment uses a Lightsail Linux **instance** with Docker Compose. GitHub Actions sends a source archive over SSH and builds the containers on the instance. PostgreSQL and uploaded files stay in the named Docker volumes because every release uses the fixed Compose project name `ragezine-portal`. The release's `.env` is a symlink to the server's private file; no production credentials are uploaded from GitHub.

## One-time instance setup

1. Create a Linux Lightsail instance, attach a static IP, and install Docker Engine with the Compose plugin. Use a deployment user with SSH access and permission to run `docker compose`. Keep PostgreSQL, port 8000, and port 8080 closed in the Lightsail firewall. Expose 80 and 443 for the public site. The GitHub-hosted deploy runner must also reach SSH on port 22. GitHub runner IP ranges change frequently, so this workflow requires SSH key authentication and an inbound SSH rule that permits the runner; restrict or disable password logins on the instance.
2. As the deployment user, create `~/ragezine-portal/shared/.env` from the repository's `.env.example` and set its permissions to `600`. Set a unique Django secret, PostgreSQL password, allowed host, `DJANGO_DEBUG=0`, email settings, and file storage credentials. Keep `RAGEZINE_HTTP_PORT=8080` unless you have a reason to change it. The deployment script discovers the published port from Compose.
3. The Compose nginx service binds to `127.0.0.1:8080`, so the app is private until an HTTPS reverse proxy is configured. When the domain is ready, put the reverse proxy in front of that local port and point DNS at the Lightsail static IP. Keep port 8080 closed in the Lightsail firewall. Configure Django's proxy and secure-cookie settings for HTTPS before accepting public submissions. To inspect the private app before then, use an SSH tunnel: `ssh -L 8080:127.0.0.1:8080 deployment@YOUR_STATIC_IP` and open `http://localhost:8080`.
4. In the GitHub repository's **Settings → Secrets and variables → Actions**, add `LIGHTSAIL_HOST` (static IP or hostname), `LIGHTSAIL_USER` (deployment user), `LIGHTSAIL_SSH_KEY` (the corresponding private SSH key), and `LIGHTSAIL_KNOWN_HOSTS` (the verified SSH host key line for the instance). Store the deployment key only in GitHub and allow its public key only for the deployment user. Verify the host key fingerprint from the instance before adding `LIGHTSAIL_KNOWN_HOSTS`.
5. Protect `main` with **Require a pull request before merging** and require the `backend-checks` and `frontend-checks` status checks. The checks appear after the workflow first runs on a PR.

After this setup, merging a PR into `main` runs checks, copies the source, builds the images, starts the stack, waits for healthy services, checks the locally served site, and records the deployed commit in `~/ragezine-portal/current`.

The workflow keeps release directories under `~/ragezine-portal/releases` for inspection or manual rollback. Monitor free disk space and prune old releases and unused Docker images when needed. Back up PostgreSQL and the upload volume or S3 bucket separately; a successful deploy is not a backup. Database migrations run during backend startup, so review migrations before merging and keep a tested restore path.
